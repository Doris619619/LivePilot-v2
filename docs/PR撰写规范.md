# LivePilot v2 PR 撰写规范

## 指定参考与适用范围

用户指定 [PR #4](https://github.com/Doris619619/LivePilot-v2/pull/4) 为结构参考。以后创建或补全 PR，都应采用它的 **固定七节、加粗主题、分组说明、逻辑与代码分离、逐项验收** 的写法。不能只保留七个标题，却在下面堆成大段流水账或写几个空泛短句。

参考的是表达结构，不是照搬旧 PR 的文案、设计结论、测试数量或能力承诺。每次以当前 `origin/main...HEAD` 的实际差异与提交记录为准，覆盖该 PR 的完整最终改动；不沿用已放弃的方案或旧分支结论。更新范围时同步重写标题与正文。

## 标题

沿用工程规范的 `<type>(<scope>)：<中文结果>`，说明用户可观察到的结果。不要使用“更新”“优化一下”等没有具体对象的标题，也不要把提交列表拼成标题。

## 固定七节与信息层级

以下二级标题必须按顺序出现，名称保持一致：

1. `Summary`
2. `背景`
3. `改动（逻辑）`
4. `改动（代码）`
5. `影响`
6. `验证`
7. `材料`

每节用简短段落或列表表达。存在多个并列主题时，每条以 **加粗的具体主题** 起头，再说明行为或结果；同一主题确有多个子项时使用一级子列表，避免多层嵌套。模块路径只在代码节集中展开，避免逻辑节和代码节重复。

### Summary：先给结论

- 通常 3–6 条，每条采用「**功能主题**：用户现在能做什么／看到什么结果」。很小的 PR 可减少条目，不凑数。
- 概括完整最终范围，不能只是列文件名或形容“高级、专业、极简”。
- 与前序 PR 的关系、已合并状态及当前审查重点，在列表后用一小段说明。

### 背景：问题与取舍

- 用 **现有痛点** 说明具体触发场景与原有问题。
- 用 **设计／实现取舍** 解释采纳的方案及原因；有多个决定时按序说明。
- 只保留帮助评审理解最终方案的约束，不复述对话过程。数据安全、共享控制模型和平台限制等关键边界在这里写清。

### 改动（逻辑）：讲使用者怎么操作

- 按登录、实例辨认、素材编排、直播控制等实际用户旅程分组；主题随本次改动选择，不机械套用。
- 每组说明入口、动作、结果，以及必要的失败／恢复／兼容行为。需要时给一个具体前后例子。
- 不展开 CSS 属性、组件 Hook 或文件路径。禁止把这节和「改动（代码）」合并。

### 改动（代码）：讲实现如何落地

- 以 **模块或路径** 为一级条目，下面说明关键状态、API、schema、布局或数据流变化。
- 解释不显然的决策，例如显示名称为何不参与控制路由、页面计时为何与状态轮询分离。
- UI 改动写清实际布局、响应式与交互策略；后端改动写清数据和协议边界。不要逐行复述 diff。

### 影响：讲兼容与边界

- 分别说明 **对用户**、**对配置与数据**、**对上下游与部署** 的实际影响；无对应影响时明确写一句。
- 有默认值、新依赖、迁移、云端与 Agent 协同升级要求时必须列出。
- 部署类改动要写备份、切换和回退边界；不能把旧备份恢复当作无风险默认步骤。
- “未改动某项”仅在有助于确认兼容性或风险边界时列出。

### 验证：逐项给证据

- 像 PR #4 一样分项列出实际执行的检查：**命令／环境**、结果、必要的测试数量或覆盖范围。
- 区分单元测试、构建、浏览器模拟验收、真实设备检查和线上部署。构建通过不等于实际开播成功；HTTP 202 不等于任务完成。
- 未完成项使用 `- [ ]`，完成后补上具体证据并改为已完成。不要把“计划验证”写成通过。
- CI 以本 PR 当前 head 的状态为准；写明真实环境验收边界，不复制历史数量或未经实测的并发、性能及可用性承诺。

### 材料：能点开、能核对

- 提供相关文档、前序 PR、截图或交付件入口。链接应指向本仓库真实存在的内容，不使用失效相对路径。
- UI PR 附可访问截图，并标注“示例数据”或真实环境及版本；不能把示例设备当成生产设备。无法附图时说明实际检查范围。
- 纯文档／后端 PR 可明确“无 UI 改动”。本机私有路径只能作为本机验收记录，不能冒充远端评审能访问的材料。
- 密码、Token、私钥、生产配置及含凭据的日志不得进入 PR、截图或 Git。测试使用独立合成凭据，私有验收值通过环境输入。

## 创建与更新检查清单

- 已检查最新 main、完整 diff 和相关提交，标题及正文覆盖最终范围。
- 七节顺序完整；加粗主题与必要的子列表让读者能快速定位信息。
- Summary 讲结果，逻辑节讲使用流程，代码节讲实现，三者各有职责。
- 验证条目来自本次实际执行；未完成与已完成明确区分。
- 示例截图、真实设备检查、线上版本明确区分，没有暴露凭据。
- PR 创建、合并、部署是不同状态。发布后更新验证项，记录合并提交、部署提交、网址及必要的回退信息；不能只因 PR 已合并就写“已上线”。

## 可复用模板

新 PR 默认使用 [.github/pull_request_template.md](../.github/pull_request_template.md)。模板是内容组织框架；删除无关提示，替换成当前变更的事实，禁止原样提交占位符。简小改动保持七节但精简各节，不为套模板虚构额外工作。
