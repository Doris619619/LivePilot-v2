# 客户端审计（2026-10-18）

## 范围与当前结论

审计覆盖本机版本与 OBS 状态、设备配对与界面状态、更新/退出安全流程和配置备份。不是全面渗透测试，也不替代真实直播发送验收。

开始审计时实际安装版本为 0.1.16，尚不能将 0.1.17 源码测试写成新版客户端已经运行。0.1.16 至 0.1.17 的 electron 更新与退出模块无代码差异。

## 实机证据

- 用户自行结束直播后，OBS 主实例 streaming=false、recording=false、reconnecting=false；Cloud 新鲜快照 phase=stopped、busy=false、lifecycle=complete。
- 客户端显示设备在线、主 OBS 控制已连接、原频道和素材仍在；另外两个 OBS 尚未启动且待配置，不把它们的不可连接状态记为已运行实例故障。
- 设置页显示版本 0.1.16，与磁盘程序 FileVersion 一致。0.1.17 尚未公开时显示最新版本符合当时发行状态。
- 没有重新开播、执行 OAuth、改动数据位置或删除设备绑定。

## 源码与专项回归

29 项测试通过：desktop-local-update、desktop-updates、desktop-update-manager、desktop-shutdown。

更新前后两次核对 OBS 推流/录制状态，排空 Agent 并刷新持久配置后才安装；排空超时不强行重启，后续失败恢复原 Agent。普通退出不自动停止 OBS。可信本地窗口提供受限更新入口，更新 DTO 不展开设备配置或凭据。

此范围暂未发现阻止升级的客户端缺陷；上述失败分支主要由自动测试验证，没有通过破坏实机网络或制造真实推流故障重演。

## 备份脚本发现与处理

历史部署脚本把活动 OBS 日志也纳入静态散列，遇到文件占用失败；发布任务索引又会随后台同步变化。两者不等于配置损坏。此次排除诊断日志，保留动态索引原始快照，补齐三个 OBS 所属标记，以备份自身内容生成完整清单。

受保护本地备份：D:/app/LiveNest-upgrade-0.1.17/backup。188 个配置相关文件，包括 11 个加密存储文件；未输出明文密钥或授权内容。

## 升级后验收

正式安装包和 Cloud 0.1.17 已上线，切换后实际 Agent 新鲜快照仍为 stopped、streaming=false、busy=false、lifecycle=complete。遵循用户要求停止使用 Computer Use，由用户在设置页手动执行“检查更新 → 更新并重启”。

用户完成更新并重新打开后，命令行验收结果：

- 磁盘 LiveNest.exe FileVersion 为 0.1.17，新客户端进程已启动；真实 Agent 在线且通过 configuration.chatConversation 能力检查。
- 备份对应的 188 个文件均存在。桌面设置解密后完整一致，三个 OBS 实例、数据位置、加密密钥和设备身份保留；只在内存比较，不输出敏感内容。
- 三份聊天检查点仅 enabledAt、sessionAt 改变，原互动配置完整保留。YouTube 仅 accessToken、expiresAt 更新，频道和 refreshToken 保留且到期时间延后，符合正常刷新。
- host.lock 随进程变化；发布索引原本就在后台同步，本次不将其字节变化解释为升级造成的数据丢失，也不声称发布作业已逐条实测。
- 使用正式 Cloud、实际 Agent 和模型进行隔离试聊：输入 `what is 谈何`，返回 clarify / ambiguous，回复 `@试聊观众 Are you asking about 谈何, or was that a typo?`。此次样本先澄清语义，没有直接展开词典解释；单次结果不代表每次生成均相同。
- 试聊前后 live-chat-read 的配置完全一致；请求只使用 live-chat-preview，没有走 YouTube 发送入口。之后新鲜快照仍为 stopped、streaming=false、busy=false、lifecycle=complete。

本次没有执行真实开播、OAuth 同意或直播间消息发送；实际观众收发仍需下一次正常直播观察。
